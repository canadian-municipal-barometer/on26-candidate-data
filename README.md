# CMB Election Study 2026: Ontario Candidate data

Via Github pages, this repo serves the manually collected candidate data for the Ontario municipalities being studied in the CMB's 2026 Ontario municipal election study.

## Branches

`main` is the production branch used to publish to Github Pages.

`dev` is used to track development before a change is ready to be put into production.

## Key Files and Locations

`data/candidate-data-versions/`: The candidate data that is loaded via the header from this repository's Github pages. Generated by `scripts/build-candidates-js.py` — do not hand-edit.

- File format: `candidates-{DATE as YYYY-MM-DD}-v{VERSION}.js`

The date and version number are in the file name and in the file's contents, under `meta`. Versioning the filename allows for easy downstream access to different versions of the data, which will be useful if the data needs to be updated mid-field. The version in `meta` makes it easy to extract that information into the final response data, which tracks the version of the data that each respondent saw. `version.txt` holds the number the next build will stamp; bump it whenever the served file changes.

Each file assigns a **lookup table** to `window.CMB_CANDIDATES`, read by `code/survey/parse-candidates.js` in the survey repo. It is not a description of the elections — that is `data/raw/candidates-raw.json`. Everything the survey writes is worked out at build time and stored under the municipality and ward that produce it, so the survey reads one entry and writes it out:

```js
municipalities["3558004"].shared = {
  names:  { mayor: [...], coun_atlarge: [...], dep_mayor: [] },
  fields: { mayor_accl: 0, atlarge: 1, atlarge_accl: 0,
            atlarge_max_votes: 5, dep_mayor_accl: "" }
}
municipalities["3558004"].wards["McIntyre"] = {
  names:  { coun_ward: [...], coun_reg: [] },
  fields: { ward: 1, ward_accl: 1, ward_max_votes: 1,
            reg_coun: 0, reg_coun_accl: "", reg_coun_max_votes: "" }
}
```

An entry comes in **two halves, and the survey reads their union**. `shared` is what the
municipality decides for every ward alike — the mayoral, at-large councillor and deputy
mayor races — held once instead of repeated in each of Toronto's 26 ward entries; the ward
entry holds the rest. The two are disjoint, so `parse-candidates.js` writes both and each
field lands exactly once, and which half a field falls in changes nothing about the export.
`meta.fields` is split the same way and says which scalars fall where. `SHARED_STEMS` in the
build script is where the split is decided, and the build aborts if two wards ever disagree
about something it holds is municipality-wide. `reg_coun` is the near miss and stays per
ward: it is elected at large in 30 of the 38 municipalities and by ward in the other 8.

- `names` holds `"LAST, First"` in the order the survey should show them, keyed by the field the survey writes them out as: `mayor1..`, `coun_ward1..`, `coun_atlarge1..`, `coun_reg1..`, `dep_mayor1..`. The three councillor lists share a prefix so they sort together in the export. A source that published no given name — Brampton's `Gursimranjit Singh, -` is the only one — gives a bare `"LAST"`, with no separator left dangling: the survey pipes these strings as choice text and `parse-recognition.js` matches them back verbatim, so a trailing `", "` both shows as a stray comma and drops the name from `__js_recog_*`. `display_name()` in the build script is where that is decided, and the build aborts on any name carrying an edge space or a dangling separator.
- Each is one contest as a voter meets it. A ward councillor race and an at-large one are never merged: Thunder Bay's respondents mark one name for their ward's seat and five for the city's, and the fields say so separately. Every at-large councillor race is `coun_atlarge`, including in the three municipalities that hold no ward race at all. `coun_reg` is the upper-tier seat however it is elected — Sarnia's second city-wide slate sits on Lambton County council, so it goes there rather than being a second at-large contest.
- `fields` is keyed by **stem** rather than by name field: each of `mayor`, `ward`, `atlarge`, `reg_coun`, `dep_mayor` writes `<stem>_accl`, and `ward`, `atlarge` and `reg_coun` add `<stem>_max_votes`. `mayor` and `dep_mayor` do not — both races are single-seat wherever they appear, so the field would read 1 in every row while implying it might not; `SINGLE_VOTE_STEMS` in the build script is where that is decided, and the build aborts if such a race ever wants more than one vote. The three councillor stems — `ward`, `atlarge`, `reg_coun` — each also carry a bare `<stem>` served-flag, 1 where the respondent is served that race and 0 where they are not; `SERVED_FLAG_STEMS` is where that is decided, and its comment is the case for keeping a field that says what a non-blank `_accl` already says. `mayor` and `dep_mayor` have none. **`meta.stems` maps stem to name field**, and is worth reading rather than guessing: the ward stem's candidate list is `coun_ward1..`, not `ward1..`.
- **A blank `_accl` or `_max_votes` means "this respondent has no such race"**, and is what the survey flow filters each question on. It means nothing else: a race whose seat count is unverified upstream would write the same blank for a contest the respondent should be asked about, so it aborts the build rather than being served. Verify it in `data/raw/by-municipality/`, or exclude the race in `notes/excluded-races.csv`. The bare `<stem>` flags say it a second way on purpose, for a survey flow that is easier to read for it, and the tests pin each to `<stem>_accl != ""` so the two cannot drift. `smd` and `mmd` said the ward race's shape a second way and were dropped for good: `ward_max_votes` gives it directly (1 single-member, 2 block vote).
- `fields` holds every scalar in final form: a number, or `""` where there is nothing to say. Every ward entry carries the same keys, as does every `shared`, so nothing can go stale between respondents.
- Every municipality has a `"99"` ward entry as well as its real wards, holding whatever is decided at large. It is what a respondent gets if they reach the question without a ward, and the only entry for the three municipalities that elect entirely at large.
- Ward pairs are stored under each ward they are drawn from, so a respondent's single-ward answer finds their ballot. Brampton and Clarington are the two.
- Name order is the one JavaScript's `localeCompare` produces, reproduced in Python so the survey does not have to sort. `tests/candidates-js.test.js` re-checks every list against `localeCompare` itself, so the two cannot drift apart silently.
- The file is pure ASCII, non-ASCII written as `\uXXXX`. It is loaded by a `<script src>` with no charset attribute, and a wrong encoding guess would stop `Ward 1 Orléans East-Cumberland` matching the ward the survey embedded.

The ward-invariant races used to repeat under every ward, which cost about 40% of the file; `shared` is what stopped that. What remains repeated is `coun_reg` in the 30 municipalities that elect it at large, kept per ward so the stem is not split across the two halves. That is the residual trade for a survey-side script that only reads and writes.

`data/csv/`: Mock candidate data for testing, from the CMB's 2025 Alberta election study. `TEST_ab-cands.csv` is the file the surname convention here follows (`BILLINGSLEY JR.` | `Ronald Stewart`).

`scripts/parse-js.R`: **Superseded** by `scripts/build-candidates-js.py`, and kept only for reference to the Alberta study. It wrapped a flat CSV in a template literal, a format Ontario's ballots do not fit: `position` had room for `mayor` and `council` only, but 20 of the 38 municipalities run more than one council race, and two of the values that would have had to go in the CSV — Brampton's `Wards 1, 5` and Guelph's `RAMOS, JR.` — contain the delimiter.

`data/raw/by-municipality/`: Hand-collected candidate names, one file per municipality, named `{census_id}-{slug}.json`. Names are recorded exactly as the source published them, alongside that municipality's notes, the page the names were read from, and a `name_format` telling the build how to split them. Hand-maintained — this is the source of truth for candidates.

- Withdrawn nominations are not part of this dataset and must not be added; the build fails if it finds one.
- A contest listed in `notes/excluded-races.csv` is still collected here, but the build drops it, so it reaches neither `candidates-raw.json` nor the served file. The three municipalities affected carry an `excluded_race` note saying what was collected and why it goes no further. Deleting the names would lose a faithful record of what the city published; the exclusion belongs to the study, not to the source.
- Sources publish names in three different shapes, hence `name_format`: `last_first` ("Chow, Olivia"), `first_last` ("Olivia Chow"), and `caps_surname` (mixed-case given name with a CAPS surname, e.g. "Jim DIODATI"). The first and third mark the surname themselves; only `first_last` leaves the boundary to be worked out.

`data/raw/candidates-raw.json`: One entry per municipality keyed by `census_id`, holding every race and its candidates. Generated by `scripts/build-candidates-raw.py` — do not hand-edit.

- Each key under `races` (`mayor`, `atlarge`, `ward`, `regional councillor`, `deputy mayor`) holds an **array** of race objects, so a municipality with two races of the same type does not collapse. Sarnia has two at-large councillor races, and Chatham-Kent has two ward tiers with different `max_votes`.
- Mayoral races are included here even though `notes/council-races.csv` excludes them by design.
- Every municipality carries the date its list was read in `notes.retrieved`. A per-municipality file may set it; otherwise it defaults to `RETRIEVED` at the top of the build script.

`scripts/build-candidates-raw.py`: Builds `data/raw/candidates-raw.json` from the per-municipality files, splitting names and attaching each race's `district_source_url` and `max_votes_source` from `notes/councillor-election-structure.csv`.

- Usage: `python3 scripts/build-candidates-raw.py`. No arguments; like the R scripts it can be run from any working directory. Install its dependencies first: `python3 -m pip install -r requirements.txt`.
- Writes only after every check passes, so a failed run leaves the previous file untouched. It aborts if a municipality or race in the structure CSV has no candidates, if a district count disagrees with `n_districts`, if a district is empty, or if a withdrawn nomination appears in the input.
- Applies `notes/excluded-races.csv`, to both the collected races and the structure CSV, so the two cannot disagree about an excluded contest whether or not the R script has been rerun since the row was added. It reports what each row dropped, and aborts if a row excluded nothing — a stale exclusion means the contest is back under a name the list no longer matches, which is the same precondition logic as `old_value` in `notes/classification-overrides.csv`.

**Splitting names.** A source that publishes "Last, First" or a CAPS surname states where the surname begins. "First Last" does not, and the last token is not a safe guess: it turns "Steven Del Duca" into `DUCA` and "Marianne Meed Ward" into `WARD`. Taking only the first token as the given name is no better — it would move a middle name into the surname for ~48 of the candidates in this data, against the convention in `data/csv/TEST_ab-cands.csv`, where a middle name stays with the given name (`BILLINGSLEY JR.` | `Ronald Stewart`).

- So the boundary is found rather than assumed. `nameparser` supplies the structure — parenthesised nicknames, suffixes, and the particles that begin a surname (`Del`, `Van`, `Da`). A name corpus (`names-dataset`) then decides whether a leftover middle token belongs to the surname, working right to left and stopping at the first token that reads as a given name. This is what keeps `MEED WARD`, `HARRISON MCINTYRE`, `NAIDOO HARRIS` and `VASQUEZ DE ESPINAL` whole while leaving `Elizabeth`, `William` and `Charles` on the given name.
- The thresholds are named constants at the top of `split_first_last()`'s section, with the reasoning for each. They are deliberately conservative: a middle token joins the surname only on positive evidence, since leaving it with the given name is what the sources themselves do.
- Some tokens are genuinely common as both — `Taylor`, `Lee`, `Blake`, `Singh` — and no rule separates a middle name from half a double-barrelled surname. Every close call is printed at the end of a run (22 of 1467 names in the current data), so the judgement calls can be eyeballed instead of being buried.

`scripts/build-candidates-js.py`: Builds the served file in `data/candidate-data-versions/` from `data/raw/candidates-raw.json`. Folds the five raw race keys into the five stems the survey writes fields for, splits ward pairs, then projects the result onto every municipality-and-ward a respondent can answer with — merging and sorting the names they are served, and settling their acclamation and vote counts. All the judgement lives here so the survey-side script does not have to make any; its header comment carries the reasoning.

- Usage: `python3 scripts/build-candidates-js.py`. No arguments, no dependencies, runnable from any working directory. Rerun it after `scripts/build-candidates-raw.py`, and bump `data/candidate-data-versions/version.txt` first if the served file is changing.
- A new build writes a new filename, so the survey's `code/survey/header.html` has to be repointed at it or respondents keep getting the old data. `parse-candidates.test.js` in the survey repo loads whichever file the header names, so a forgotten repoint fails there rather than in the field.
- Writes only after every check passes. It aborts if a race key is unknown, if a municipality has no mayoral or council race, if two races under one stem both claim a ward, or if a ward pair cannot be split.
- Prints the number of embedded data fields the Qualtrics flow has to declare per family (`mayor1..37 coun_ward1..16 coun_atlarge1..15 coun_reg1..13 dep_mayor1..3` as the data stands), and which municipality sets each maximum. The flow declares these by hand — under the survey's own `__js_` prefix, as `__js_mayor1` — so a longer list than any here means adding fields to the flow.
- **Aborts on any race whose seat count or `max_votes` is unverified upstream.** Acclamation cannot be computed for those, and the blank they used to be served with now means "no such race" to the survey flow — so serving one would hide a real contest from the people who vote in it. Fix it in `data/raw/by-municipality/`, or put the race in `notes/excluded-races.csv` if the study is not asking about it. This was a warning until the flow started filtering on blankness; Kitchener's and Cambridge's at-large regional races were the only two it ever named, and both are excluded now.

`notes/`: Ballot structure data for the municipalities in the study — which of them let a voter mark more than one name in a single race, and why the SMD/MMD coding alone cannot answer that. See `notes/SOURCES.md` for the reasoning and a source URL for every finding.

- `notes/council-races.csv`, `notes/classification-overrides.csv` and
  `notes/excluded-races.csv` are hand-maintained.
- `notes/excluded-races.csv` is the record of which contests the study leaves out, one row
  per contest keyed by `census_id` + `office`. Today it is three rows: Cambridge's,
  Kitchener's and Waterloo's regional councillors, whose holders sit on Regional Council
  and not on city council. It is read by `scripts/build-candidates-raw.py`, which drops
  those races and their candidates, and by `scripts/get-municipal-data.R`, which refuses
  to emit a `council-races.csv` row for an excluded contest. See `notes/SOURCES.md`,
  "The three upper-tier-only contests are excluded from the study".
- `notes/election-type-ward-type.csv` (one row per municipality) and `notes/councillor-election-structure.csv` (one row per race, with the municipality's attributes repeated across its rows) are generated by `scripts/get-municipal-data.R` — do not hand-edit either.
- `notes/contest-candidate-counts.csv` (one row per contest, with how many candidates it currently has) is generated by `scripts/build-contest-candidate-counts.py` — do not hand-edit.

`scripts/get-municipal-data.R`: Rebuilds both generated files above from the master municipality list and the study's municipality Google Sheet, applying the corrections in `notes/classification-overrides.csv` and deriving ballot structure from `notes/council-races.csv`.

- Usage: `Rscript scripts/get-municipal-data.R`. Like the other scripts here, it can be run from any working directory.
- Needs `googlesheets4` auth and access to the master municipality list under `CMB Data/`, which it reads by absolute path.

`scripts/build-contest-candidate-counts.py`: Counts the candidates in `data/raw/candidates-raw.json` and writes `notes/contest-candidate-counts.csv`, one row per district in that file — the grain a voter actually sees, so Ottawa's councillor race is 24 rows rather than one row of 68.

- Usage: `python3 scripts/build-contest-candidate-counts.py`. No arguments, no dependencies, runnable from any working directory. Rerun it after `scripts/build-candidates-raw.py`; it only counts and adds nothing of its own.
- Sorted by candidate count, largest first; ties fall back to ballot order, so the sort is stable across runs.
- Coarser tables are a group-by away: by `census_id` + `office` for the race grain of `notes/councillor-election-structure.csv`, by `census_id` for the municipality.
- A row is keyed by `census_id` + `office` + `district`, and the build aborts if that is ever not unique. The parent race's ballot structure — its district count, seats and `max_votes` — is not repeated here; it is one join on `census_id` + `office` away in the structure CSV.
- The counts are a snapshot and a lower bound until nominations close (2026-08-21) and the certified lists follow (2026-08-24). Each row carries the `retrieved` date of the municipality's list.

`tests/`: Checks on the generated data that the build scripts cannot make themselves, because they hold across files or across columns that are filled in separately.

- Usage: `node --test` from the repo root. No dependencies and no `package.json`; it uses Node's built-in runner. `node --test <dir>` is not supported — pass a file if you want to run just one.
- `tests/candidates-js.test.js` checks the newest built file in `data/candidate-data-versions/` against `data/raw/candidates-raw.json`: that no candidate was lost or invented, that each respondent was served their own ward and no other, that the names are in `localeCompare` order, and that the acclamation, vote-count and ballot-shape fields follow from the raw numbers. That is where the survey's values are verified, since the build is what decides them.
- It also reads `notes/excluded-races.csv` and checks that no ward of a listed municipality serves the excluded race, and that it is absent from `candidates-raw.json` too. The "no candidate was lost" check cannot see an exclusion — the race is already gone from the raw file it compares against — so this is the check that the drop actually happened.
- It also re-derives `PUNCT_ORDER` from `localeCompare` and checks the build script's copy against it. That constant is the one part of the sort that had to be found by experiment rather than reasoned out, so it is checked rather than trusted; the name-order test alone would only exercise the character pairs today's names happen to produce.
- `tests/structure-csv.test.js` asserts that `seats_per_district` equals `max_votes` for every race in `notes/councillor-election-structure.csv`. The two are separate measures — seats filled vs. names a voter may mark — that happen to coincide while every contest in the study is single-seat or plurality-at-large. It is a tripwire: a failure is either a typo or a municipality adopting limited or cumulative voting, and the fix belongs in `notes/council-races.csv` followed by a rerun of `scripts/get-municipal-data.R`.
